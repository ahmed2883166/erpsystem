# مراجعة أنواع البيانات قبل ترقية PostgreSQL

## مصدر المراجعة وحدودها

تم فحص artifact الرسمي `nexus-postgresql-schema-baseline` من تشغيل NEXUS ERP رقم `44066690449` على الفرع `feature/company-setup-currency-tax-activity`، عند commit `b3c3af0c7c4e6c6a38eb4ebccbf8018d618e53bb`.

المخطط مولّد من قاعدة SQLite جديدة ومؤقتة بعد تشغيل مهيئات التطبيق الحقيقية؛ لا يحتوي بيانات شركة. هذه مراجعة للمخطط، وليست ترحيلًا للبيانات أو اعتمادًا لمخطط PostgreSQL للإنتاج.

الـViews الفعلية في المخطط الحالي صفر. لكن مولّد DDL لم يكن يرفض وجود Views في مخطط مستقبلي؛ لذلك أضيفت حماية fail-closed واختبارات تمنع إسقاطها بصمت. الحماية لا تغيّر ناتج المخطط الحالي ذي الـViews الصفرية.

## لماذا لا تتحول الـ270 عمودًا آليًا؟

قائمة المرشحين مبنية على أسماء الأعمدة فقط، وهي نقطة بداية للمراجعة وليست خريطة تحويل معتمدة. من أمثلة المطابقات غير الرقمية التي ظهرت بسبب التشابه في الاسم:

- JSON وسجلات التدقيق: `activity_profiles.tax_roles_json` وحقول `audit_log.*_values`.
- أرقام تعريف ضريبية: `branches.tax_number`, `customers.tax_number`, `suppliers.tax_number`؛ يجب أن تظل نصوصًا للحفاظ على الأصفار البادئة والتنسيقات.
- تواريخ: `fx_exchange_rates.rate_date`, `sales_credit_notes.credit_date`, `supplier_credit_notes.credit_date`.
- قيم وصفية/تصنيفية: `discount_type`, `depreciation_method`, `tax_treatment`, `tax_notes`, `tax_reference`, `discount_approval_status`, `basic_salary_change_reason`.
- حقول قد تحتوي وقتًا أو نصًا مرجعيًا مثل `payroll_lines.basic_salary_reference` وحقول `*_paid_at` لا يصح افتراض أنها أرقام.

وفي المقابل توجد حقول مالية وكميات ومعدلات تستحق مراجعة دقيقة، مثل `journal_lines.debit`, `journal_lines.credit`, `sales_invoice_lines.unit_price`, `stock_valuation_layers.value_remaining`, وحقول الرواتب والضرائب. يجب اعتماد الدقة والمقياس لكل مجموعة وفق قواعد العمل، لا وفق الاسم وحده.

## قواعد التحويل المطلوبة قبل اعتماد أي خريطة

1. إبقاء المعرفات وأرقام الضرائب والباركود والحسابات المرجعية والتواريخ والنصوص وJSON كما هي.
2. عدم تحويل أي حقل مالي إلى `REAL` أو `DOUBLE PRECISION`؛ يلزم `NUMERIC(p,s)` بدقة ومقياس محددين بعد فحص الاستخدامات والحدود.
3. تحديد المقياس بحسب المجال: مبالغ العملة، أسعار الوحدات، الكميات، نسب الضرائب/التأمين، وأسعار الصرف ليست بالضرورة ذات نفس الدقة.
4. مراجعة كل حقل مرشح مقابل عمليات القراءة والكتابة والتقريب والمقارنة والتصدير، وليس اسم العمود فقط.
5. اختبار round-trip لقيم مثل الأصفار، الأرقام السالبة، القيم الكبيرة، الكسور الدقيقة، والقيم القديمة المخزنة كنص.
6. إبقاء DDL الناتج أداة تصميم فقط إلى أن تكتمل خريطة التحويل واختبارات البيانات على نسخ مؤقتة.

## الإجراء المنفذ

أضيف إلى `scripts/generate_postgres_schema.py` رفض صريح لأي مخطط يحتوي Views غير مترجمة، مع اختبارين:
- يرفض View غير مترجم بدل إسقاطه بصمت.
- يقبل المخطط الحالي عندما تكون قائمة Views فارغة.

لم يتم تحويل أي عمود TEXT إلى نوع رقمي جديد، ولم يتم ربط PostgreSQL بتطبيق Flask، ولم يتم تغيير قاعدة SQLite أو بيانات الشركة.
