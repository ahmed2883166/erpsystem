# المرحلة الثانية — خط أساس مخطط PostgreSQL

## الحالة

هذا المستند يصف خط أساس توليد DDL من المخطط الفعلي. لا يعني أن التطبيق أصبح يعمل على PostgreSQL، ولا يغير محرك SQLite الحالي.

مصدر المخطط: GitHub Actions artifact باسم `nexus-initialized-sqlite-schema`، الناتج من تهيئة التطبيق على قاعدة جديدة مؤقتة. المصدر المرجعي الحالي: الفرع `feature/company-setup-currency-tax-activity`.

## ما يفعله مولّد PostgreSQL

الملف `scripts/generate_postgres_schema.py` ينتج خط أساس محافظًا:

- `INTEGER PRIMARY KEY` يتحول إلى `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- أعمدة INTEGER الأخرى تتحول إلى BIGINT، وREAL إلى DOUBLE PRECISION.
- أعمدة TEXT تظل TEXT في هذه المرحلة، بما فيها مبالغ القيود والفواتير والمخزون والمرتبات.
- ينقل المفاتيح الخارجية بعد إنشاء جميع الجداول، حتى لا تتعطل العلاقات الدائرية.
- ينقل الفهارس العادية والفريدة والتعبيرية.
- ينقل CHECK constraints من تعريفات الجداول.
- يحول الـ21 Trigger الموجودة: حماية سجلات التدقيق من التعديل والحذف، تحديث إصدار بيانات لوحة الإدارة، والتحقق من ارتباط مواقع الأصناف بالمخزن الصحيح.
- يعالج قيد SQLite `COLLATE NOCASE UNIQUE` في جدول الأدوار بفهرس فريد على `lower(column)`.

## لماذا لا نحول المبالغ إلى NUMERIC الآن؟

البرنامج الحالي يخزن كثيرًا من القيم المالية كسلاسل نصية ويحسبها عبر Decimal ودوال SQLite مخصصة مثل:

- `DECIMAL_SUM`
- `DECIMAL_NET`
- `DECIMAL_LAYER_VALUE_SUM`
- `DECIMAL_RUNNING_NET`

التحويل الآلي إلى NUMERIC دون مراجعة الدقة والمقياس لكل حقل قد يغيّر التقريب أو نتائج تقارير تاريخية. لذلك يحافظ خط الأساس على النص كما هو، ولا يمرر أي مبلغ عبر float. ينتج المولد قائمة مرشحين للمراجعة في ملف JSON منفصل.

## اختبار PostgreSQL

يضيف Workflow خدمة PostgreSQL 16 مؤقتة، ثم:

1. ينشئ مخطط SQLite مؤقتًا من تهيئة NEXUS.
2. يولد ملف DDL وملف مراجعة لأنواع الحقول.
3. ينفذ DDL في schema مؤقت مستقل داخل PostgreSQL.
4. يتحقق من عدد الجداول والمفاتيح والفهارس وصلاحية الفهارس.
5. يحذف schema الاختبار في النهاية.

ملفات التنفيذ:
- `scripts/export_initialized_sqlite_schema.py`
- `scripts/inspect_sqlite_schema.py`
- `scripts/generate_postgres_schema.py`
- `scripts/validate_postgres_schema.py`
- `tests/test_postgres_schema_generator.py`

## ما لم يتم بعد

- لم يتغير `database.py` أو مسارات تشغيل التطبيق لاستخدام PostgreSQL.
- لم يتم تحويل SQL placeholders من `?` إلى صيغة PostgreSQL.
- لم يتم استبدال `sqlite_master` وPRAGMA.
- لم يتم استبدال `lastrowid` بـ `RETURNING`.
- لم يتم تحويل `INSERT OR IGNORE` أو معالجة معاملات `BEGIN IMMEDIATE`.
- لم يتم استبدال دوال Decimal الخاصة بـSQLite باستعلامات/دوال PostgreSQL.
- لم يتم نقل النسخ الاحتياطي والاستعادة من آلية ملفات SQLite إلى آلية PostgreSQL.
- لم يتم اعتماد تحويلات NUMERIC النهائية أو تشغيل بيانات شركة حقيقية.

## بوابة الاعتماد

لا نبدأ توصيل التطبيق بـPostgreSQL إلا بعد نجاح اختبار DDL على PostgreSQL 16، ومراجعة ملف المرشحين الرقميين، ثم تنفيذ طبقة اتصال مستقلة واختبارات توافق لكل وحدة. يظل SQLite هو محرك التشغيل الحالي حتى اجتياز هذه المراحل.
