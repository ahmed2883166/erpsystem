**الغرض:** توثيق ما ثبت وجوده في المصدر، وما يحتاج اختبار قبول أو استكمال. هذا السجل ليس شهادة اكتمال وظيفي.

## ضوابط لا تتغير

- العمل على الفرع المحدد فقط، وعدم تعديل `main`.
- عدم تشغيل اختبارات على قاعدة بيانات الشركة أو مجلد بياناتها؛ الاختبارات على قواعد مؤقتة ومعزولة فقط.
- عدم تنفيذ migrations بنيوية أو تعديل أرصدة/قيود موجودة ضمن مرحلة الجرد.
- عدم اعتبار وجود route أو template أو اختبار منفرد دليلًا كافيًا على اكتمال دورة العمل.
- لا تصنيع: لا BOM ولا أوامر إنتاج ولا تحويل خام إلى تام.
- الضرائب ضمن مصر والسعودية فقط، دون تكامل مباشر مع ETA أو ZATCA.

## 2) فجوات مؤكدة أو مخاطر تحتاج إغلاقًا

1. **تعدد الشركات:** لم يثبت وجود نموذج شركة قانونية مستقل وعزل شامل للبيانات. لا تبدأ إضافة `company_id` قبل تصنيف الجداول والاستعلامات وخطة ترحيل آمنة.
2. **الفروع:** يوجد ربط جزئي للمخازن والأبعاد التحليلية؛ لا يثبت أن جميع المستندات والقيود والمستخدمين مقيدون بفرعهم.
3. **مطابقة المشتريات:** الوثائق السابقة تسجل أن المطابقة الجزئية على مستوى سطور أمر الشراء والاستلام والفاتورة تحتاج قبولًا شاملًا. يجب اختبار الكمية والقيمة ومنع إعادة تخصيص نفس الجزء.
4. **التسوية البنكية:** وجود شاشة مطابقة لا يثبت اكتمال استيراد كشف البنك أو التسوية الجزئية أو تفسير الفروق.
5. **الضرائب:** وجود مركز ضريبي لا يثبت مطابقة متطلبات مصر والسعودية أو جاهزية الإقرار. يجب التحقق من إعدادات الضريبة والمدخلات والمخرجات حسب الدولة والفترة دون تكامل مباشر.
6. **قاعدة البيانات:** الاعتماد الحالي على SQLite يحتاج قياسًا واختبار تزامن قبل ادعاء الجاهزية للشركات المتوسطة والكبيرة؛ WAL لا يحول SQLite إلى قاعدة متعددة الكتابات.
7. **التوثيق:** توجد وثائق قديمة وأخرى مواصفات مستقبلية؛ يجب فصل «موجود في الكود» عن «مطلوب» وعن «اجتاز اختبار قبول».

## 3) خطة التدقيق التفصيلي التالية

### A. قاعدة البيانات والعلاقات
- استخراج كل الجداول والأعمدة والمفاتيح والفهارس وقيود UNIQUE وFOREIGN KEY من كل وحدات التهيئة.
- تصنيف كل جدول: إعداد عام، شركة، فرع، مستند، حركة، سجل أمني، أو بيانات مرجعية.
- مراجعة الحذف والتعطيل والتاريخ المرجعي ومنع حذف المستندات المرحلة.
- مراجعة الترحيلات على نسخة قديمة ونسخة فارغة داخل مجلد مؤقت فقط.

### B. الصلاحيات والأمان
- استخراج كل Flask route وكل decorator والصلاحية الفعلية التي يتحقق منها الخادم.
- اختبار الوصول المباشر وطلبات POST لكل دور، بما فيها التلاعب بمعرف المستند.
- فحص CSRF والجلسات ورفع الملفات وسجل التدقيق ورسائل HTTP 500.
- تسجيل أي مسار بلا حماية صريحة كعنصر مراجعة، لا كفشل مؤكد قبل فهم سياقه.

### C. الدورات التشغيلية والمحاسبية
- شراء: طلب → أمر → استلام جزئي/كامل → فاتورة → GRNI → إشعار دائن → سداد.
- بيع: عرض/أمر → فاتورة → صرف مخزون وتكلفة مبيعات → تحصيل جزئي/كامل → مرتجع/رد.
- مخزون: استلام وصرف وتحويل وجرد وتسوية وتشغيلة وصلاحية وتكلفة ومطابقة الأستاذ.
- مرتبات: إدخال يدوي → اعتماد فروق الأساسي → ترحيل → سداد → عكس مضبوط.
- أصول: إضافة → إهلاك دوري → بيع/استبعاد → ربح/خسارة ومطابقة.
- بنك: كشف بنكي → مطابقة → فروق → تسوية → ربط الأستاذ.
- عملات وفترات: إعادة تقييم، إقفال وافتتاح، ومنع تكرار الأرصدة.

### D. التقارير والواجهة
- مطابقة القوائم والدفاتر وكشوف الأطراف مع الأستاذ العام.
- مطابقة قيمة المخزون ودفاتر البنوك والأصول والمرتبات مع حساباتها.
- مراجعة الفلاتر والتواريخ والأبعاد والصلاحيات والتصدير والطباعة.
- قياس زمن الاستجابة على بيانات اختبارية كبيرة دون استخدام بيانات الشركة.

## 4) قواعد تصنيف النتيجة

- **مكتمل ومختبر:** الوظيفة موجودة، ومساراتها الأساسية والاستثنائية اجتازت اختبار قبول مناسبًا.
- **موجود ويحتاج استكمال:** يوجد تنفيذ فعلي لكن توجد فجوات أو اختبارات قبول ناقصة.
- **غير موجود:** لا يوجد تنفيذ فعلي بعد التحقق من المصدر.
- **غير محسوم:** الأدلة الحالية لا تكفي للحكم.

لا تُرقّى أي وظيفة إلى «مكتمل ومختبر» اعتمادًا على اسم ملف أو route أو اختبار وحدة منعزل.
