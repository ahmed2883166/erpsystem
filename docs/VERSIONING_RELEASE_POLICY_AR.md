# سياسة إصدارات NEXUS ERP وإدارة النشر

## 1. نظام ترقيم الإصدارات

يعتمد المشروع Semantic Versioning بصيغة:

`MAJOR.MINOR.PATCH`

- **MAJOR:** تغيير غير متوافق في الواجهات أو البيانات أو السلوك، أو ترقية معمارية تتطلب خطوات انتقالية.
- **MINOR:** وظائف جديدة متوافقة مع الاستخدام والبيانات الحالية.
- **PATCH:** إصلاح أخطاء وتحسينات آمنة لا تغيّر التوافق المقصود.
- **Pre-release:** نسخ التطوير والاختبار مثل `0.8.0-alpha.1` أو `1.0.0-rc.1`.

لا يعني كل Commit إصدارًا جديدًا. يمكن أن يحتوي الإصدار الواحد على عدة commits وPull Requests.

## 2. سياسة NEXUS الحالية

- النسخة الحالية في README موسومة `v0.1`، وهي مرحلة تطوير/تجربة داخلية وليست إصدارًا إنتاجيًا.
- لا يتم إعلان `v1.0.0` إلا بعد اجتياز بوابة الجاهزية والقبول الواردة في `docs/NEXUS_ERP_MASTER_ROADMAP_AR.md`.
- لا تنشأ Tags أو GitHub Releases رسمية بأثر رجعي لمجرد وجود commits.
- لا نرفع رقم الإصدار عند كل تعديل صغير؛ نحدد رقم الإصدار عند تجهيز حزمة مستقرة ومختبرة.

### أمثلة

| التغيير | رقم الإصدار المتوقع |
|---|---|
| أول إصدار مستقر بعد اعتماد بوابة الإنتاج | `1.0.0` |
| إضافة وحدة موافقات متوافقة | `1.1.0` |
| إصلاح خطأ في احتساب تقرير دون تغيير التوافق | `1.1.1` |
| تغيير قاعدة بيانات أو API بطريقة تكسر التوافق | `2.0.0` |
| نسخة اختبار قبل الإصدار | `1.2.0-rc.1` |

## 3. استراتيجية الفروع

- `main`: الإصدارات المستقرة المعتمدة فقط.
- `develop`: تجميع التطويرات بعد اعتماد وجود هذا الفرع في سير العمل.
- `feature/<name>`: ميزة محددة أو وحدة محددة.
- `release/<version>`: تثبيت النطاق، مراجعة الإصدار، إصلاحات القبول.
- `hotfix/<name>`: إصلاح عاجل لنسخة منشورة.

**الوضع الحالي:** فرع العمل المعروف هو `feature/company-setup-currency-tax-activity`. لا يُنشأ أو يُعاد توجيه `develop` أو `main` تلقائيًا بهذه الوثيقة. ولا يتم الدمج أو النشر دون موافقة مالك المشروع.

## 4. خطوات تجهيز Release

1. اختيار commit مستهدف من فرع التطوير.
2. مراجعة التغييرات والاعتمادات والملفات المتأثرة.
3. تشغيل الاختبارات والـstatic checks والـbenchmarks المناسبة.
4. التأكد أن نتائج CI تخص نفس commit المراد إصداره.
5. اختبار ترقية قاعدة بيانات من نسخة سابقة على نسخة اختبارية.
6. إنشاء نسخة احتياطية واختبار استعادتها في قاعدة منفصلة.
7. مراجعة Release Notes وملف CHANGELOG.
8. إعداد Tag مثل `v1.0.0` على commit المعتمد.
9. إنشاء GitHub Release مع وصف التغييرات وتعليمات الترقية.
10. الاحتفاظ بحزمة الإصدار السابقة وخطة الرجوع.
11. بعد موافقة مالك المشروع فقط، يتم الدمج إلى `main` والنشر.

## 5. محتويات كل Release

- رقم الإصدار وتاريخ الإصدار.
- الجديد Added.
- التحسينات Changed.
- الإصلاحات Fixed.
- التغييرات غير المتوافقة Breaking Changes.
- تغييرات قاعدة البيانات وملفات Migration.
- إعدادات البيئة الجديدة أو المتغيرة.
- خطوات النسخ الاحتياطي والترقية.
- طريقة الرجوع الآمن إن أمكن.
- نتيجة الاختبارات ورابط CI المرتبط بالـcommit.
- القيود المعروفة Known Issues.

## 6. قواعد قاعدة البيانات

- لا تعتمد على استرجاع الكود وحده للتراجع عن migration.
- migrations تكون إضافية ومحافظة على البيانات وقابلة للتحقق.
- اختبر الترقية من قاعدة قديمة فعلية منزوعة البيانات الحساسة.
- لا تشغّل migrations على قاعدة المستخدم الحقيقية أثناء التطوير.
- يجب أن تتضمن تعليمات الإصدار نسخة احتياطية قبل الترقية، والتحقق من integrity بعد الترقية.
- أي migration غير قابلة للعكس يجب أن توثق ذلك صراحةً وتوفر خطة استعادة.

## 7. قوالب أسماء الوسوم والإصدارات

- Tag: `vMAJOR.MINOR.PATCH`
- Pre-release: `vMAJOR.MINOR.PATCH-alpha.N`, `-beta.N`, `-rc.N`
- Branch: `release/1.0.0`
- Hotfix: `hotfix/fix-invoice-posting`

لا تستخدم أرقامًا مثل `version 2` لكل تعديل؛ الترقيم الدلالي يوضح حجم التغيير ومدى التوافق.

## 8. عدم التفويض التلقائي

إنشاء Tag أو GitHub Release أو دمج إلى `main` أو نشر البرنامج إجراءات اعتماد منفصلة. توثيق هذه السياسة لا يمثل موافقة مسبقة على أي منها.
