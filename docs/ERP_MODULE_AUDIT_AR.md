## 2. ملاحظات معمارية ظهرت أثناء الفحص

1. أسماء بعض الـBlueprints لا تطابق صيغة صلاحياتها أو مسمياتها، مثل Blueprint المشتريات `purchase` مع صلاحيات `purchases.*`. يجب الحفاظ على تغطية التدقيق والصلاحيات عند إضافة وحدات جديدة.
2. يوجد محرك ترحيل مشترك `accounting_core.post_journal`، ويجب أن يكون المسار الإلزامي لأي وحدة جديدة.
3. التطبيق يفعّل `CSRFProtect` وإعدادات Cookie للجلسة في `app.py`. توجد وثائق أقدم تصف غياب حماية CSRF؛ يجب تحديثها بعد اختبار جميع النماذج والاستثناءات بدل اعتبار الوصف القديم حقيقة حالية.
4. `SQLite WAL` يحسن تزامن القراءة، لكنه لا يوفر تعدد كتابات حقيقيًا؛ خطة الشركات المتوسطة والكبيرة تحتاج قرارًا موثقًا بشأن PostgreSQL قبل التوسع الفعلي.
5. توجد وحدات متعددة مسجلة في التطبيق، لكن وجود Blueprint لا يثبت اكتمال دورة العمل أو الصلاحيات أو التقارير.
6. بعض الوثائق في README و`docs/INTEGRATION_ARCHITECTURE_AR.md` تحمل أوصافًا قديمة لا تتفق بالضرورة مع الملفات الحالية؛ يلزم توحيد الوثائق بعد مراجعة كل وحدة.

## 3. فجوات مؤسسية ذات أولوية عالية

الحالات التالية لم تُثبت كوظائف مكتملة من جرد المسارات الأولي، ولذلك تعامل كمتطلبات تحتاج فحصًا وتنفيذًا:

| المتطلب | الحالة الأولية | الإجراء المطلوب |
|---|---|---|
| تعدد الشركات وعزل البيانات | غير مثبت | فحص schema لكل الجداول وcompany scope في كل query وroute |
| تعدد الفروع والمواقع التشغيلية | جزئي/غير مثبت | تحديد نموذج الفرع وربطه بالمستندات والمخازن والمستخدمين |
| معاملات بين الشركات Intercompany | غير مثبت | تصميم البيع/الشراء البيني والتسويات والقيد المتقابل |
| محرك موافقات عام | غير مثبت | تصميم Approval Workflow قابل لإعادة الاستخدام |
| ترقيم مستندات مستقل لكل شركة/فرع/سنة | غير مثبت | بناء Numbering Service ذري يمنع التصادم |
| سجل مرفقات ومستندات | غير مثبت | ربط الملفات بالمستندات مع فحص النوع والحجم والصلاحيات |
| مركز إشعارات ومهام | غير مثبت | مهام وموافقات متأخرة وتنبيهات قابلة للتتبع |
| CRM والفرص | جزئي/غير مثبت | فحص عروض الأسعار ثم بناء lead/opportunity/activity |
| إدارة المشروعات والمقاولات | غير مثبت | مشروع، عقد، مستخلص، مقاول باطن، ضمان، تكلفة وربحية |
| التصنيع وBOM وMRP | مؤجل عمدًا | لا يبدأ قبل استقرار المخزون والتكلفة |
| الصيانة وإدارة الأسطول | غير مثبت | وحدات تخصصية بعد اكتمال النواة |
| API موثق | غير مثبت | تصميم API versioning ومصادقة وصلاحيات وحدود استخدام |

## 4. مخاطر يجب حسمها قبل تعدد الشركات

- هل كل جدول تشغيلي يحتوي `company_id` أو يمكن اشتقاق الشركة بأمان من علاقة غير قابلة للتغيير؟
- هل كل استعلام قراءة وتعديل وحذف يقيّد النتائج بالشركة المصرح بها؟
- هل يمكن لمستخدم تابع لشركة A الوصول إلى مستند شركة B بتغيير رقم URL؟
- هل أرقام الفواتير والقيود والمخازن فريدة داخل الشركة أم على مستوى قاعدة البيانات كلها؟
- هل دليل الحسابات موحد للمجموعة أم مستقل لكل شركة؟ وكيف تتم مطابقة Intercompany؟
- هل العملة الأساسية والضريبة والسنة المالية وإعدادات النشاط على مستوى الشركة أم على مستوى النظام؟
- كيف تعالج المعاملات المشتركة بين الفروع والشركات دون ازدواج أو فقد أثر التدقيق؟

**لا نضيف `company_id` عشوائيًا إلى الجداول ولا نبدأ migration قبل وضع نموذج عزل بيانات موحد ومراجعة كل الاستعلامات.**

## 5. خطة التدقيق التالية

### التدقيق A — قاعدة البيانات
- استخراج كل `CREATE TABLE` والعلاقات والفهارس.
- تصنيف الجداول إلى إعدادات عامة، شركة، فرع، مستند، حركة، سجل تدقيق.
- مراجعة المفاتيح الخارجية وقيود UNIQUE.
- تحديد الجداول التي تفتقر إلى company/branch scope.
- اختبار migrations على قاعدة قديمة ونسخة فارغة.

### التدقيق B — الصلاحيات والأمان
- جرد كل route مع decorator والصلاحية.
- اختبار الوصول المباشر إلى URL وPOST دون صلاحية.
- فحص CSRF والجلسات والملفات المرفقة وتسجيل العمليات.
- اختبار عزل الشركة والفرع بعد تصميمهما.

### التدقيق C — الدورات المحاسبية
- شراء حتى السداد.
- بيع حتى التحصيل.
- استلام وصرف وتحويل وجرد.
- أصول وإهلاك واستبعاد.
- رواتب حتى السداد.
- بنك وتسوية.
- عملات وإعادة تقييم.
- سنة مالية وإقفال وافتتاح.

### التدقيق D — التقارير
- مطابقة كل تقرير مع مصدره المحاسبي.
- فحص pagination والتصدير والفلاتر.
- مطابقة أرصدة الأطراف والمخزون والبنوك مع الأستاذ العام.
- مراجعة IAS 7 والقوائم والنسب.

## 6. قرار التنفيذ التالي

أول مشروع تطوير فعلي بعد هذا التدقيق هو **Enterprise Core – نموذج الشركات والفروع وعزل البيانات**، لكن لا يبدأ coding قبل إنهاء التدقيق A وB وتحديد استراتيجية قاعدة البيانات. بناء تعدد الشركات فوق استعلامات غير معزولة قد يسبب تسرب بيانات بين الشركات، وهو خطر غير مقبول في ERP مؤسسي.
