# نموذج أولي لطبقة اتصال PostgreSQL — المرحلة التالية

## الحالة

تمت إضافة `postgres_database.py` كطبقة اتصال مستقلة للتجربة فقط. لا يستوردها التطبيق ولا تغيّر `database.py` ولا إعدادات تشغيل Flask. SQLite يظل محرك التشغيل الوحيد.

## العقد الحالي

- DSN صريح أو متغير بيئة مستقل: `NEXUS_POSTGRES_DSN`.
- لا يوجد fallback تلقائي إلى SQLite ولا اختيار تلقائي للمحرك.
- استخدام psycopg 3 عند استدعاء الدالة فقط؛ المكتبة اختيارية وليست ضمن متطلبات التشغيل الأساسية.
- الصفوف الافتراضية قواميس؛ هذا مقصود وواضح وليس توافقًا زائفًا مع `sqlite3.Row`.
- قيم PostgreSQL من نوع NUMERIC ترجع `Decimal` دون المرور عبر float.
- `autocommit=False` افتراضيًا، ويمكن تفعيله صراحة.
- مهلة الاتصال الافتراضية 5 ثوانٍ وبحد أقصى 30 ثانية.
- اسم التطبيق يمرر إلى PostgreSQL لأغراض التعرف على اتصالات NEXUS.

## الاختبارات

تُشغّل اختبارات الاتصال فقط عند وجود `NEXUS_TEST_POSTGRES_DSN`، وتستخدم جداول TEMP على اتصال الاختبار. تغطي:
- إنشاء الاتصال وصفوف القاموس.
- حفظ واسترجاع Decimal بدقة.
- rollback وعدم اعتماد المعاملة ضمن الوضع الافتراضي.
- autocommit الصريح.
- رفض الإعدادات غير الصالحة وعدم وجود DSN.

Workflow الاختبارات يوفّر PostgreSQL 16 مؤقتًا ويفعّل DSN الاختبار. في بيئات Python الأخرى التي لا تحتوي على DSN، تُتخطى اختبارات التكامل فقط.

## ما لا تدّعيه هذه المرحلة

هذه ليست طبقة بديلة لـSQLite وليست جاهزة لتشغيل أي وحدة ERP. ما زالت هناك أعمال لازمة قبل توصيل التطبيق:
- توحيد row access بين `sqlite3.Row` ونتائج PostgreSQL.
- تحويل placeholders من `?` إلى `%s` أو اعتماد واجهة استعلام موحدة.
- معالجة `lastrowid` باستخدام `RETURNING`.
- نقل `INSERT OR IGNORE` وPRAGMA وsqlite_master.
- تحويل معاملات `BEGIN IMMEDIATE` وسياسة التزامن.
- استبدال دوال Decimal المسجلة في SQLite.
- ترحيل النسخ الاحتياطي والاستعادة.
- مراجعة حقول المبالغ والكميات وتحديد NUMERIC(p,s) لكل حقل قبل ترحيل بيانات حقيقية.

لا يتم تفعيل PostgreSQL في التطبيق إلا بعد إكمال هذه الأعمال واختبار كل وحدة محاسبيًا ووظيفيًا.
