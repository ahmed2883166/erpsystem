# تقرير تدقيق النواة المؤسسية — المرحلة صفر (دفعة 1)

**تاريخ الفحص:** 15 نوفمبر 2026  
**المستودع:** `ahmed2883166/erpsystem`  
**الفرع:** `feature/company-setup-currency-tax-activity`  
**Commit المفحوص:** `08191031ee209b840000021622accfdd00ad5b3f`  
**نطاق هذه الدفعة:** مراجعة مصدر قاعدة البيانات الأساسية، إعداد الشركة، الجلسات والصلاحيات، وسجل التدقيق.  
**حدود التقرير:** هذه دفعة تدقيق مصدرية وليست اعتمادًا أمنيًا أو محاسبيًا نهائيًا، ولم يتم تعديل قاعدة بيانات تشغيلية.

## 1. نتيجة مهمة: إعداد الشركة الحالي ليس نموذج تعدد شركات

في `app.py`، التهيئة الأساسية تنشئ جدول `company_settings` بمفتاح `setting_key` وقيمة `setting_value`، وتخزن بيانات مثل اسم الشركة والدولة والنشاط والعملة الأساسية في صفوف إعدادات عامة. شاشة `/company/setup` تقرأ وتحدث هذه الإعدادات العامة.

لم يظهر في مخطط الجداول الأساسية المعروض داخل `initialize_database()` جدول شركات قانونية مستقل أو جدول فروع، كما أن جدولَي `accounts` و`journal_entries` الأساسيين لا يحتويان `company_id` أو `branch_id`.

**القرار:** النسخة الحالية لا يجوز وصفها بأنها متعددة الشركات أو معزولة البيانات. لا نضيف أعمدة `company_id` عشوائيًا ولا نفتح إعداد تعدد الشركات قبل حصر كل الجداول والاستعلامات والعلاقات في الوحدات.

## 2. ما ثبت وجوده في النواة

| المجال | دليل المصدر | النتيجة الحالية |
|---|---|---|
| إعداد الشركة | `company_settings` وroute `/company/setup` | إعداد مفرد عام، وليس سجل شركة مستقل |
| دليل الحسابات | `accounts` مع `parent_id` و`is_group` | شجرة حسابات أساسية موجودة؛ لا يوجد نطاق شركة ظاهر في الجدول الأساسي |
| اليومية | `journal_entries` و`journal_lines` | محرك قيود أساسي؛ لا يوجد نطاق شركة ظاهر في الجدول الأساسي |
| المستخدمون | `users` و`roles` وصلاحيات مخزنة | أدوار وصلاحيات موجودة؛ المستخدم غير مربوط بشركة/فرع في المخطط الأساسي |
| الفترات | `accounting_periods` | جدول فترات أساسي؛ يلزم فحص تطبيق قفل الفترة على كل مسارات الترحيل |
| سجل التدقيق | `audit_log` مع before/after وrequest_id وفهارس | سجل موسع موجود |
| منع تعديل سجل التدقيق | trigger يمنع UPDATE وDELETE على `audit_log` | حماية على مستوى SQLite موجودة |
| حماية الجلسة | HttpOnly وSameSite=Lax وانتهاء 30 دقيقة | إعدادات موجودة؛ Secure مشروط بتفعيل HTTPS صراحة |
| CSRF | `CSRFProtect(app)` | حماية عامة مفعلة؛ يلزم جرد الاستثناءات والنماذج |
| كلمات المرور | PBKDF2-SHA256 مع ترقية تجزئات SHA-256 القديمة عند الدخول | آلية حديثة موجودة مع مسار توافق قديم |
| HTTP 500 | ملف تدوير مستقل `data/logs/http_500.log` ورسالة عامة | تسجيل خادمي ورسالة آمنة موجودان |

## 3. ضوابط تمنع كسر البيانات الحالية

- تغيير النشاط الأساسي بعد وجود قيود مرحلة مرفوض في مسار تفعيل ملف النشاط، ويطلب تحويلًا محاسبيًا معتمدًا.
- قوالب الحسابات تُضاف/تُراجع عبر وظائف التهيئة دون حذف الحسابات أو تغيير معرفاتها في مسار التهيئة الظاهر.
- سجل التدقيق append-only عبر triggers.
- لا يوجد في هذه الدفعة أي migration أو تعديل على بيانات الشركة.

## 4. المخاطر المفتوحة التي تتطلب فحصًا قبل أي تعدد شركات

1. حصر كل `CREATE TABLE` في ملفات `stock.py`, `purchases.py`, `sales.py`, `banking.py`, `fixed_assets.py`, `workforce.py`, `financial_planning.py`, `currency_center.py`, `tax_center.py` وغيرها.
2. استخراج كل مفاتيح الربط بين المستندات والقيود والعملاء والموردين والأصناف والمخازن والمستخدمين.
3. فحص كل استعلام SELECT/UPDATE/DELETE وكل route يستخدم معرف مستند قادمًا من URL؛ لا يكفي وجود صلاحية عامة لإثبات عزل البيانات.
4. جرد صلاحيات routes في كل Blueprint، بما فيها عمليات العرض والتصدير والاعتماد والعكس.
5. اختبار منع الوصول المباشر إلى مستندات مستخدم/فرع/شركة أخرى بعد تحديد نموذج العزل؛ لا يوجد حاليًا أساس كافٍ لاختبار عزل شركات حقيقي.
6. حسم PostgreSQL كخيار تشغيلي للشركات المتوسطة والكبيرة قبل توسيع الكتابات المتزامنة؛ SQLite WAL لا يحول SQLite إلى قاعدة متعددة الكتّاب.

## 5. قرار التنفيذ

**لا ننشئ جداول شركات وفروع الآن.** الخطوة الآمنة التالية هي إكمال جرد الجداول والاستعلامات والصلاحيات في جميع الوحدات، ثم تصميم نموذج نطاق موحد يشمل الشركة والفرع مع خطة ترقية واختبارات على نسخة قديمة ونسخة فارغة.

بعد اكتمال ذلك فقط نبدأ Enterprise Core: الشركات، الفروع، عضوية المستخدمين، ترقيم المستندات، الموافقات العامة، وربط الأبعاد، مع الحفاظ على كل القيود والأرصدة التاريخية.
