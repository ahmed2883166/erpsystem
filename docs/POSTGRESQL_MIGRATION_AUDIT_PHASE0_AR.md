# تدقيق نقل NEXUS ERP إلى PostgreSQL — المرحلة صفر

تاريخ التدقيق: 17 نوفمبر 2026

## 1. حدود التدقيق

- تمت مراجعة شجرة المستودع على نسخة الأساس: 286 ملفًا، منها 115 ملف Python.
- تمت قراءة طبقة الاتصال `database.py`، ومسارات البيانات `app_paths.py`، ومنطق المحاسبة `accounting_core.py`، وآلية النسخ والاستعادة `backup_restore.py`، وملفات المتطلبات والاختبارات ذات الصلة.
- أُجري مسح ساكن لملفات Python بحثًا عن أنماط SQLite الشائعة. أعداد التطابقات في المسح ليست عدد استعلامات SQL المؤكدة؛ فقد تشمل نصوص الاختبارات أو التعليقات أو علامات الاستفهام داخل النصوص.
- لم تُنفذ أي تغييرات على مخطط قاعدة البيانات أو بيانات الشركات، ولم يبدأ تحويل أي وحدة تشغيلية إلى PostgreSQL في هذه المرحلة.

## 2. النتيجة التنفيذية

النقل ممكن، لكنه ليس استبدالًا لمكتبة الاتصال فقط. اعتماد التطبيق على SQLite موزع بين طبقة الاتصال، وتعريفات الجداول، وترقيات المخطط، والاستعلامات، ومعالجة الصفوف والأخطاء، والنسخ الاحتياطي.

**التوصية:** اعتماد PostgreSQL كقاعدة تشغيل مستهدفة، مع إبقاء SQLite متاحة للاختبارات الحالية مؤقتًا. ننفذ النقل على دفعات صغيرة، ولا نغيّر قاعدة التشغيل الافتراضية قبل اجتياز اختبارات التكافؤ المحاسبي والتشغيلي.

## 3. نقاط الاعتماد على SQLite التي ظهرت في المصدر

### أ. طبقة الاتصال والصفوف

- `database.py` يستورد `sqlite3` مباشرة، ويضبط `row_factory=sqlite3.Row` وخصائص `PRAGMA`.
- وحدات متعددة تستورد `sqlite3` ليس فقط للاتصال، بل أيضًا لالتقاط أنواع أخطاء SQLite.
- الكود يستخدم الوصول إلى الصفوف بالاسم، وفي مواضع أخرى بالترتيب الرقمي؛ لذلك يجب أن يحافظ محول PostgreSQL على سلوك متوافق أو تُعدّل المواضع صراحة.
- `requirements.txt` لا يحتوي حاليًا على مشغل PostgreSQL مثل psycopg 3.

### ب. صياغة SQL

ظهرت الأنماط التالية في ملفات التطبيق:

- معاملات SQL بعلامة `?`، بينما مشغل PostgreSQL يستخدم صيغة معاملات مختلفة.
- `.lastrowid` للحصول على المعرّفات المنشأة؛ البديل المعتاد في PostgreSQL هو `INSERT ... RETURNING id`.
- `INSERT OR IGNORE`؛ يحتاج إلى تحويل مقصود إلى `ON CONFLICT ... DO NOTHING` مع تحديد قيد التعارض الصحيح، لا استبدال نصي أعمى.
- `sqlite_master` و`PRAGMA table_info` لفحص الجداول والأعمدة.
- `executescript` وتعريفات/تعديلات جداول وقت التشغيل داخل عدد من الوحدات.
- `BEGIN IMMEDIATE` في معاملات حساسة؛ لا يُنقل حرفيًا إلى PostgreSQL، لأن نموذج القفل والتزامن مختلف.
- دوال تاريخ SQLite مثل `strftime` في بعض الاستعلامات.

### ج. الوحدات الأعلى أولوية في التحويل

1. `app.py`: تهيئة قاعدة البيانات والمخطط المركزي، وعدد كبير من الاستعلامات والمعاملات.
2. `accounting_core.py`: الترحيل المحاسبي، التحقق من توازن القيود، اكتشاف الجداول والأعمدة، ودوال التجميع العشري.
3. `sales.py` و`purchases.py`: كثافة استعلامات ومعاملات مرتفعة وارتباط مباشر بالمخزون والأستاذ.
4. `stock.py`: ترحيلات وإعادة بناء جداول، وعمليات إدراج وتعارضات.
5. `workforce.py` و`workforce_extras.py`: عدد كبير من الاستعلامات وإجراءات المرتبات والموارد البشرية.
6. `banking.py` و`fixed_assets.py` و`financial_planning.py` و`cash_commitments.py` و`currency_center.py` و`period_adjustments.py`.
7. `backup_restore.py` و`backup_scheduler.py`: مسار منفصل؛ النسخ الاحتياطي والاستعادة الحاليان يعتمدان على ملفات SQLite ولا يصلحان كآلية PostgreSQL.

## 4. نقطة محاسبية حرجة: دقة المبالغ

- `accounting_core.py` يستخدم `Decimal` ودوال SQLite مخصصة مثل `DECIMAL_SUM` و`DECIMAL_NET` و`DECIMAL_LAYER_VALUE_SUM` و`DECIMAL_RUNNING_NET`.
- توجد أعمدة مبالغ مخزنة كنصوص في المخطط الحالي، ويجب عدم تحويلها عبر `float` أثناء النقل.
- PostgreSQL يدعم `NUMERIC` بدقة عشرية؛ لكن التحويل يتطلب جرد كل عمود مالي، وتحديد الدقة والمنازل العشرية، ومقارنة إجماليات المصدر والهدف باستخدام `Decimal`.
- يجب اختبار التجميع والرصيد الجاري وتقارير الأستاذ والمخزون والضرائب قبل اعتماد أي تحويل لنوع عمود مالي.

**شرط قبول إلزامي:** لا يُقبل النقل إذا اختلف إجمالي المدين أو الدائن، أو رصيد أي حساب، أو قيمة المخزون، أو أرصدة العملاء والموردين، أو إجمالي المرتبات والضرائب ولو بفارق تقريب غير مفسر.

## 5. تصميم التنفيذ المقترح

### المرحلة 0 — تثبيت خط الأساس (هذه المرحلة)

- تثبيت SHA المرجعي.
- حصر أنماط SQLite والوحدات المتأثرة.
- تحديد اختبارات التكافؤ المحاسبي والتشغيلي.
- عدم تغيير قاعدة التشغيل أو بيانات المستخدم.

### المرحلة 1 — فصل مخطط قاعدة البيانات عن التشغيل

- تجميع إنشاء الجداول وتعديلاتها في ترحيلات مرقمة ومرتبة.
- إيقاف الاعتماد التدريجي على إنشاء/تعديل المخطط أثناء فتح الصفحات أو تنفيذ الطلبات.
- توثيق الجداول والفهارس والقيود والعلاقات وأنواع المبالغ.
- الحفاظ على ترحيلات SQLite الحالية حتى لا تتعطل قواعد الاختبار أو التثبيت القائمة.

### المرحلة 2 — طبقة اتصال متعددة المحركات

- بناء واجهة موحدة للاتصال والمعاملات وتنفيذ الاستعلامات.
- إبقاء SQLite مدعومة أثناء التطوير.
- إضافة PostgreSQL باستخدام psycopg 3 بعد حسم توافق الصفوف والمعاملات ومعاملات SQL.
- منع التحويلات النصية العامة غير الآمنة للاستعلامات؛ التحويل يتم بمحول واعٍ بصياغة SQL أو بتعديل الوحدة واختبارها.
- عدم وضع قواعد محاسبية داخل محول قاعدة البيانات.

### المرحلة 3 — إثبات التوافق على النواة المحاسبية

- تشغيل اختبارات إنشاء القيود، التوازن، التكرار الآمن، العكس، الفترات المغلقة، الأبعاد التحليلية، والأرصدة.
- إضافة اختبارات تكافؤ SQLite/PostgreSQL على قاعدة اختبار مؤقتة.
- التحقق من سلوك المعاملات والتراجع والتزامن.

### المرحلة 4 — نقل الوحدات على دفعات

الترتيب المقترح: الحسابات والأستاذ ← المبيعات والمشتريات ← المخزون ← البنوك والنقدية والأصول ← المرتبات والموارد البشرية ← الضرائب والعملات والتقارير.

لا تُنقل دفعة قبل اجتياز اختبارات الدفعة السابقة واختبارات الانحدار.

### المرحلة 5 — النسخ والاستعادة والتشغيل

- بناء نسخ احتياطي واستعادة مخصصين لـ PostgreSQL، مع اختبار استعادة فعلي.
- اختبار الأداء والتزامن على أحجام بيانات متدرجة، ثم اختبار 30 مستخدمًا وبيانات تاريخية كبيرة متوازنة.
- إعداد خطة تحويل وعودة (cutover/rollback) موثقة، مع نسخة احتياطية قابلة للاستعادة قبل التحويل.
- لا يتم تغيير قاعدة التشغيل الافتراضية إلا بعد موافقة واختبار قبول نهائي.

## 6. قرارات حماية لا يجوز تجاوزها

- العمل على `feature/company-setup-currency-tax-activity` فقط، وعدم لمس `main`.
- عدم حذف أو إعادة إنشاء قاعدة بيانات الشركة أو جداولها بغرض تسهيل النقل.
- الاختبارات تستخدم قواعد مؤقتة ومعزولة؛ ممنوع استخدام مجلد `data/` للاختبارات.
- لا يتم تحويل المبالغ إلى أعداد عائمة.
- لا تتغير قواعد الترحيل المحاسبي أو سياسات الضرائب أو المرتبات أثناء مشروع النقل.
- لا يتم حذف أي وظيفة قائمة أو تغيير سلوكها دون طلب وموافقة مستقلين.
- لا يُعلن نجاح النقل أو CI إلا بعد التحقق من SHA الدقيق وسجلات GitHub Actions.

## 7. الخطوة التنفيذية التالية

بدء المرحلة 1 بجرد موحد للمخطط: كل الجداول والأعمدة والمفاتيح والفهارس والقيود ومواقع إنشائها أو تعديلها، ثم إعداد ترحيلات مرقمة قابلة للتشغيل على SQLite وPostgreSQL. بعد ذلك فقط نبدأ أول تعديل برمجي في طبقة الاتصال، مع اختبار محاسبي صغير ومتكافئ على المحركين.

## 8. الحالة عند كتابة هذا المستند

- اكتمل التدقيق الأولي لأنماط SQLite وطبقة الاتصال.
- لم تتم إضافة psycopg أو SQLAlchemy إلى المتطلبات.
- لم يتم إنشاء اتصال PostgreSQL أو تعديل أي وحدة تشغيلية.
- لم يتم نقل بيانات أو تغيير قاعدة التشغيل.
- هذا المستند توثيق لنتائج التدقيق وخطة التنفيذ، وليس ادعاءً بأن PostgreSQL أصبح مدعومًا بالفعل.
