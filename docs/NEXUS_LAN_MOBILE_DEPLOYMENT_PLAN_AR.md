# خطة تشغيل NEXUS ERP على الشبكة المحلية والموبايل

> الحالة: خطة تنفيذ معتمدة مبدئيًا على فرع التطوير فقط. هذه الوثيقة لا تغيّر طريقة تشغيل النظام ولا تفتح أي منفذ شبكي بذاتها.

## 1. الهدف والنطاق

تشغيل نسخة واحدة من NEXUS ERP على جهاز مركزي داخل مقر الشركة، بحيث يدخل المستخدمون من أجهزة الكمبيوتر والهواتف عبر المتصفح، ويتعامل الجميع مع قاعدة بيانات مركزية واحدة.

- أجهزة الكمبيوتر: المحاسبة، المخازن، المشتريات، المبيعات، الموارد البشرية والإدارة.
- الهواتف: واجهة المتصفح المتجاوبة للوصول إلى الوظائف المسموح بها حسب صلاحية المستخدم.
- النطاق الأول: شبكة LAN داخل الشركة فقط.
- خارج النطاق في هذه المرحلة: الوصول من الإنترنت أو من خارج الشركة، تطبيق Android/iOS مستقل، ومزامنة قواعد بيانات متعددة.

## 2. نتيجة فحص الوضع الحالي

| المجال | الموجود حاليًا | المطلوب قبل الاعتماد |
|---|---|---|
| خادم التطبيق | Flask يعمل عبر Waitress، والحزمة موجودة في requirements.txt | تثبيت إعداد تشغيل واضح للخادم المركزي وإدارة بدء التشغيل والتوقف |
| عنوان الاستماع | app.py يستخدم HOST مع قيمة افتراضية 127.0.0.1 | جعل إعداد LAN صريحًا وآمنًا، مع توثيق كيفية الرجوع إلى localhost |
| قاعدة البيانات | SQLite مع WAL وbusy_timeout ومفاتيح خارجية | إبقاء ملف قاعدة البيانات على قرص محلي في جهاز الخادم، واختبار الكتابة المتزامنة والنسخ والاستعادة |
| تعدد المستخدمين | Waitress بعدد threads افتراضي 8 وصلاحيات مستخدمين | اختبار سيناريوهات الاستخدام المتزامن وعدم تشغيل عدة عمليات تطبيق على ملف SQLite نفسه |
| واجهة الهاتف | viewport ووسائط CSS موجودة بالفعل | مراجعة كل النماذج والجداول والقوائم على شاشات صغيرة وإصلاح نقاط التعثر |
| النسخ الاحتياطي | توجد آلية نسخ احتياطي مجدولة ونسخة SQLite متسقة | اختبار النسخ والاستعادة من جهاز آخر والتحقق من صلاحيات مجلد النسخ |
| الجلسات والحماية | CSRF، HttpOnly، SameSite=Lax، وانتهاء جلسة بعد 30 دقيقة | تحديد سياسة HTTPS داخل الشبكة، وضبط Secure cookies عند استخدام HTTPS، ومراجعة كلمات المرور الافتراضية |
| التوثيق | README يذكر LAN، لكن قيمة HOST الافتراضية في app.py حاليًا هي 127.0.0.1 | توحيد الوثائق مع إعداد التشغيل الفعلي |

## 3. التصميم المستهدف

1. جهاز Windows مخصص أو موثوق يعمل كخادم مركزي.
2. تثبيت Python والاعتماديات على الخادم فقط.
3. تشغيل تطبيق NEXUS بواسطة Waitress كعملية خدمة واحدة.
4. تخزين قاعدة البيانات ومجلد البيانات والنسخ الاحتياطية على أقراص محلية بالخادم، وليس داخل مجلد شبكة SMB مشترك.
5. تخصيص عنوان IP ثابت أو DHCP reservation للخادم، مثل 192.168.1.10.
6. السماح بالوصول إلى منفذ التطبيق من شبكة Private/LAN فقط عبر Windows Firewall.
7. المستخدم يفتح عنوان الخادم من Chrome أو Edge أو متصفح الهاتف، ويسجل الدخول بحسابه وصلاحياته.
8. لا يتم تثبيت قاعدة بيانات أو نسخة مستقلة من البرنامج على أجهزة المستخدمين.

## 4. مراحل التنفيذ

### المرحلة 0 — خط أساس واختبارات حماية البيانات

- تثبيت نسخة احتياطية قابلة للاستعادة قبل أي تغيير.
- تسجيل إصدار Python ونسخة النظام ومسار قاعدة البيانات.
- مراجعة إعدادات المستخدمين، كلمات المرور، الصلاحيات، وملفات الأسرار.
- اختبار تسجيل الدخول والخروج وCSRF وانتهاء الجلسة.
- التأكد أن الاستعادة لا تستبدل قاعدة البيانات أثناء وجود مستخدمين نشطين.

**بوابة الانتقال:** نجاح استعادة نسخة اختبارية والتحقق من سلامة قاعدة البيانات وعدم تأثر القيود المرحلة.

### المرحلة 1 — إعداد الخادم المحلي

- معالجة إعداد HOST بحيث يمكن تشغيل التطبيق على واجهة الشبكة عند اختيار وضع LAN، مع إبقاء localhost خيارًا للتطوير.
- إضافة إعدادات تشغيل موثقة للمنفذ وعدد Waitress threads.
- توفير ملف تشغيل Windows واضح، مع فحص المتغيرات والمسارات قبل بدء الخدمة.
- إعداد Windows Firewall للسماح بالاتصال من الشبكة المحلية الخاصة فقط.
- توثيق معرفة عنوان IP للخادم وطريقة الوصول من الأجهزة الأخرى.
- عدم تشغيل Flask development server في التشغيل المشترك.

**بوابة الانتقال:** فتح صفحة الدخول من جهاز كمبيوتر ثانٍ ومن هاتف على نفس شبكة Wi-Fi، مع بقاء الدخول المحلي ممكنًا.

### المرحلة 2 — قاعدة البيانات والتزامن

- إبقاء SQLite على قرص محلي بالخادم مع WAL وbusy_timeout.
- تشغيل نسخة واحدة فقط من تطبيق NEXUS على ملف قاعدة البيانات.
- تنفيذ اختبارات متزامنة تشمل: قيدين، فاتورتين، حركتي مخزون، تحصيلين، ومسير رواتب تجريبي.
- التحقق من عدم تكرار الترحيل أو فقدان تحديثات أو ظهور أخطاء database is locked.
- اختبار النسخ الاحتياطي أثناء وجود قراءات وعمليات تشغيلية، ثم اختبار الاستعادة في بيئة منفصلة.
- وضع حدود تشغيلية واضحة لعدد المستخدمين. إذا أصبح عدد الكتاب المتزامنين أو حجم الفروع أكبر من قدرة SQLite، تُنفذ دراسة انتقال مستقلة إلى PostgreSQL قبل التوسع؛ لا يتم النقل تلقائيًا ضمن هذه المرحلة.

**بوابة الانتقال:** تطابق أرصدة الأستاذ والمخزون والذمم قبل وبعد اختبارات الضغط، وعدم وجود قيود غير متوازنة أو حركات مكررة.

### المرحلة 3 — تجربة الموبايل (Responsive QA)

- مراجعة تسجيل الدخول، لوحة الإدارة، القوائم، البحث، النماذج، الجداول، والطباعة.
- جعل عناصر اللمس مناسبة، ومنع تجاوز عرض الشاشة أفقيًا إلا داخل الجداول التي تحتاج تمريرًا أفقيًا.
- التأكد من أن القوائم الجانبية لا تحجب مساحة العمل على الهاتف.
- اختبار القيود وسندات القبض والصرف وفواتير البيع والمشتريات وحركات المخزون والموظفين والمرتبات.
- إبقاء التقارير الكبيرة قابلة للقراءة، مع عدم التضحية بدقة الأرقام أو حقول الإدخال.
- اختبار Chrome على Android وEdge/Chrome على Windows بأحجام شاشة مختلفة.

**بوابة الانتقال:** إتمام السيناريوهات الأساسية من الهاتف دون الحاجة إلى وضع Desktop أو فقدان حقول أو أزرار.

### المرحلة 4 — الحماية والتشغيل اليومي

- فرض كلمات مرور قوية وتغيير بيانات الدخول الافتراضية قبل التشغيل.
- إنشاء حساب مستقل لكل موظف، بأقل صلاحيات لازمة، ومنع مشاركة الحسابات.
- تفعيل HTTPS داخل الشبكة عند اعتماد شهادة موثوقة للأجهزة، ثم تفعيل Secure session cookies.
- إبقاء CSRF مفعّلًا وعدم السماح بالوصول المباشر إلى ملف SQLite.
- قصر جدار الحماية على Private network وعناوين الشبكة الداخلية؛ عدم فتح المنفذ على Public network أو الإنترنت.
- إعداد النسخ الاحتياطي اليومي والاحتفاظ بعدد نسخ مناسب، مع نسخة إضافية خارج جهاز الخادم.
- كتابة إجراء واضح للتوقف والصيانة والاستعادة، وتسجيل المسؤول عن كل إجراء.

**بوابة الانتقال:** مراجعة أمنية وتشغيلية، وتجربة استعادة موثقة، وموافقة المسؤول قبل إدخال بيانات فعلية.

### المرحلة 5 — قبول التشغيل

- اختبار دخول عدة مستخدمين في الوقت نفسه.
- اختبار الصلاحيات ومنع المستخدم من تنفيذ وظيفة غير مصرح بها.
- اختبار سلامة القيود والفواتير والمخزون والمرتبات والتقارير.
- اختبار فقد الاتصال بالشبكة ثم عودته، والتأكد من عدم تكرار إرسال النموذج أو المستند.
- توثيق زمن فتح الصفحات والتقارير على الشبكة.
- اعتماد قائمة الأجهزة والمستخدمين وعنوان الخادم وخطة النسخ الاحتياطي.

## 5. معايير القبول النهائية

- الكمبيوتر والهاتف يصلان إلى نفس عنوان NEXUS ونفس قاعدة البيانات.
- لا توجد قاعدة بيانات منفصلة على أجهزة المستخدمين.
- صلاحيات المستخدم مطبقة بنفس الطريقة من الكمبيوتر والموبايل.
- لا تتكرر المستندات أو القيود عند إعادة المحاولة أو انقطاع الاتصال.
- الأرقام المحاسبية والمخزنية لا تتغير بسبب تحسينات الواجهة أو إعداد الشبكة.
- النسخ الاحتياطي والاستعادة مجربان عمليًا.
- التطبيق لا يكون متاحًا من الإنترنت في هذا الإصدار المحلي.

## 6. قرارات وحدود لا يجوز تجاوزها

- لا تعديل أو حذف للقيود المرحلة أو أرصدة الفترات المقفلة أثناء تنفيذ هذه الخطة.
- لا تشغيل لعدة نسخ مستقلة من التطبيق على ملف SQLite واحد.
- لا وضع لملف SQLite على مشاركة شبكية بين الأجهزة.
- لا فتح للمنفذ على الإنترنت أو شبكات عامة.
- لا ترحيل إلى PostgreSQL إلا بعد خطة منفصلة واختبارات ترحيل ومطابقة.
- لا اعتبار نجاح الوصول من المتصفح دليلًا على جاهزية النظام المحاسبية للإنتاج؛ يلزم اجتياز اختبارات القبول المحاسبية والتشغيلية.

## 7. الملفات المتوقع تعديلها أثناء التنفيذ

- app.py: إعداد عنوان الاستماع وتشغيل Waitress.
- README.md: تعليمات LAN الفعلية ومتطلبات الأمان.
- scripts/ أو deployment/: ملفات إعداد وتشغيل Windows وفحص البيئة.
- templates/base.html وstatic/style.css: تحسينات تجربة الهاتف عند ثبوت الحاجة.
- tests/: اختبارات إعداد الخادم والتزامن وسيناريوهات واجهة الهاتف حيث يمكن أتمتتها.
- docs/: سجل خطوات التثبيت والتشغيل والاستعادة وقائمة قبول التشغيل.

**حالة التنفيذ:** هذه الوثيقة هي خطة التنفيذ فقط. لم يتم تغيير عنوان الاستماع، أو فتح منافذ، أو تعديل قاعدة البيانات، أو نشر البرنامج نتيجة إضافة هذه الخطة.
