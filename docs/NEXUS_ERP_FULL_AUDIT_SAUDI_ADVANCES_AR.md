# مراجعة NEXUS ERP الشاملة وخطة توطين مقدمات العملاء للسعودية

**الفرع:** `feature/company-setup-currency-tax-activity`  
**Commit الأساس:** `3e750a6603ad563fde3c194f1e3e1d19decd50f8`  
**نوع المراجعة:** مراجعة مصدرية للملفات والوحدات والاختبارات المتاحة؛ ليست اعتمادًا إنتاجيًا أو مراجعة أمنية مستقلة.

## 1. ملخص تنفيذي

المستودع يحتوي على نواة محاسبية ووحدات تشغيلية فعلية للمبيعات والمشتريات والمخزون والبنوك والأصول والموارد البشرية والضرائب والعملات والتقارير والنسخ الاحتياطي. وجود الوحدة أو نجاح اختبارات الوحدة لا يعني اكتمالها كدورة ERP مؤسسية.

**القرار:** لا نبدأ بإضافة وحدات كثيرة قبل إغلاق فجوات التكامل، وعزل الشركات، والتوطين الضريبي. الأولوية هي سلامة دفتر الأستاذ وربط كل مستند تشغيلي به، ثم ضوابط المؤسسة.

## 3. فجوات مؤسسة ذات أولوية حرجة

### P0 — قبل تجربة تشغيل شركة فعلية

1. **عزل الشركات (Tenant Isolation):** جرد كل الجداول والاستعلامات ومسارات GET/POST. لا يوجد في هذه المراجعة إثبات كافٍ أن كل سجل تشغيلي وكل استعلام مقيد بـ `company_id`. لا نضيف الحقل عشوائيًا قبل نموذج بيانات وترحيل موحد.
2. **مطابقة المستند مع الأستاذ:** اختبار مستند ← قيد ← أستاذ مساعد ← ميزان مراجعة ← قوائم مالية، مع عكس المستندات وتواريخها.
3. **المعاملات والتزامن:** ضمان ذرية العمليات التي تنشئ مستندًا وقيدًا وتحديث رصيد، ومنع ازدواج العملية عند إعادة الطلب أو طلبين متزامنين.
4. **الفترات المالية:** منع الترحيل والتعديل داخل الفترات المغلقة من كل الوحدات، وليس من شاشة القيود فقط.
5. **استعادة النسخ:** اختبار استعادة نسخة فعلية إلى قاعدة منفصلة والتحقق من القيود والأرصدة والمرفقات.

### P1 — قبل التوسع المتوسط/الكبير

- نموذج شركات وفروع ومخازن ومراكز تكلفة ومشروعات موحد.
- محرك موافقات Maker-Checker قابل لإعادة الاستخدام مع فصل الإنشاء والاعتماد والترحيل.
- Numbering Service ذري بحسب الشركة/الفرع/السنة/نوع المستند.
- مرفقات ومستندات مؤيدة بصلاحيات وفحص ملفات وسجل تنزيل.
- API موثق بإصدارات ومصادقة وحدود طلبات.
- تنبيهات ومهام ومواعيد استحقاق وموافقات معلقة.
- قاعدة بيانات PostgreSQL قبل حمل مؤسسي متزامن؛ SQLite/WAL مناسب لمرحلة التطوير/النطاق المحدود ولا يحقق توسع الكتابة المطلوب بمفرده.

### P2 — وحدات تخصصية بعد استقرار النواة

- إدارة المشروعات والمقاولات والمستخلصات ومقاولي الباطن والاحتجازات والضمانات.
- CRM والفرص والأنشطة.
- صيانة وأسطول.
- التصنيع وBOM وMRP (مؤجل عمدًا في نطاق الإصدار الأول).
- ذكاء أعمال ومستودع بيانات وتقارير موحدة.

## 4. توطين مقدمات العملاء — السعودية مؤقتًا

### القرار الوظيفي

يُعتمد نظام ضريبة القيمة المضافة السعودي كمرجعية أولى لمقدمات العملاء في هذا المسار. لا يتم تغيير إعدادات كل الشركات تلقائيًا، ولا يتم تغيير الافتراضي المصري العام للتطبيق لمجرد هذا القرار. يجب أن تتبع المعالجة إعدادات الشركة الضريبية عند تشغيلها.

### الأساس الضريبي

- القاعدة العامة في الاتفاقية الموحدة: تستحق الضريبة عند التوريد أو إصدار الفاتورة أو استلام المقابل جزئيًا/كليًا، أيها أسبق، وفي حدود المبلغ المستلم.
- النسبة الأساسية السعودية 15% للتوريدات الخاضعة، مع وجود توريدات صفرية أو معفاة أو خارج النطاق.
- التوريدات المستمرة وبعض العقود الحكومية لها قواعد خاصة؛ لا يجوز تطبيق قاعدة عامة آلية عليها دون تحديد نوع التوريد.
- يجب إصدار المستند الضريبي المناسب وفق متطلبات الفوترة الإلكترونية والتوقيت النظامي، ولا يعني إنشاء إيصال قبض داخلي أنه فاتورة إلكترونية معتمدة أو تم إرساله إلى فاتورة.

### متطلبات التصميم قبل الترحيل

1. التمييز بين **دفعة مقدمة مقابل توريد خاضع** وبين **تأمين/عربون قابل للرد لا يمثل مقابلاً للتوريد**. التأمين القابل للرد لا يفرض عليه VAT تلقائيًا.
2. تحديد تصنيف التوريد: قياسي 15%، صفر، معفى، خارج النطاق، أو معاملة خاصة.
3. تحديد هل قيمة المقبوض شاملة VAT أم غير شاملة؛ لا نفترض ذلك من رقم الإيصال.
4. حفظ معدل الضريبة والمعاملة والوعاء والضريبة وتاريخ الاستحقاق في سجل الحركة حتى لا تتغير المعاملة التاريخية عند تعديل إعدادات الشركة.
5. عند إصدار الفاتورة النهائية، يجب خصم الضريبة التي سبق الإقرار عنها على الدفعة من الضريبة المستحقة على إجمالي التوريد، مع الحفاظ على إجمالي ضريبة التوريد الصحيح وعدم احتساب الضريبة مرتين.
6. تخصيص الدفعة على فواتير مختلفة المعدلات/المعاملات يجب أن يوزع الوعاء والضريبة على أساس واضح، وإلا يُمنع التخصيص الآلي ويطلب توزيعًا تفصيليًا.
7. الرد أو العكس يجب أن ينشئ مستندًا/قيدًا ضريبيًا عكسيًا قابلًا للتتبع، لا حذفًا أو تعديلًا للقيد المرحّل.
8. تضمين دفعات العملاء المستحقة ضريبيًا في تقرير VAT بحسب تاريخ الاستحقاق، مع مرجع المستند الضريبي.
9. حالات العقود الحكومية والتوريدات المستمرة تحتاج حقولًا/سياسات خاصة أو مراجعة يدوية؛ لا تدخل تلقائيًا في القاعدة القياسية.
10. لا ندعي تكامل ZATCA أو إصدار XML/QR أو إرسال/قبول فاتورة إلكترونية قبل تنفيذ واجهة التكامل واجتياز اختبارات المطابقة الرسمية.

### نموذج قيد توضيحي

إذا استلمت المنشأة 1,150 ريالًا **شامل الضريبة** كدفعة مقابل توريد قياسي خاضع بنسبة 15%، يكون التحليل الحسابي:
- الوعاء = 1,000 ريال.
- ضريبة المخرجات = 150 ريالًا.
- إجمالي المقبوض = 1,150 ريالًا.

القيد المبدئي المقترح بعد تحديد الاستحقاق:
- من حـ/ البنك أو الصندوق 1,150
- إلى حـ/ التزامات دفعات العملاء المقدمة 1,000
- إلى حـ/ ضريبة قيمة مضافة مستحقة 150

أما إذا كان المبلغ 1,150 **غير شامل الضريبة**، فالإجمالي المحصل يصبح 1,322.50 والضريبة 172.50. لذلك يجب أن يحدد المستخدم طريقة إدخال المبلغ بوضوح.

هذا مثال للدفعة القياسية الخاضعة فقط، وليس قاعدة لكل العربون أو التأمين أو العقود.

## 5. اختبارات قبول لازمة لمقدمات السعودية

| الاختبار | النتيجة المطلوبة |
|---|---|
| دفعة خاضعة شاملة VAT | فصل الوعاء والضريبة بدقة 15/115 |
| دفعة خاضعة غير شاملة VAT | احتساب 15% فوق الوعاء |
| دفعة صفرية/معفاة/خارج النطاق | عدم إنشاء ضريبة مخرجات |
| تأمين قابل للرد | عدم احتساب VAT تلقائيًا |
| دفعة جزئية ثم فاتورة نهائية | عدم ازدواج ضريبة الدفعة |
| دفعة واحدة موزعة على فواتير بمعدلات مختلفة | توزيع ضريبي صحيح أو رفض العملية غير المحددة |
| رد دفعة قبل الفاتورة | عكس الضريبة والوعاء وفق سبب الرد والمستند |
| عكس إيصال أو تخصيص | قيود عكسية وتاريخية محفوظة |
| تقرير VAT شهري | إدراج الضريبة في فترة استحقاقها |
| عقد حكومي/توريد مستمر | تطبيق سياسة خاصة أو إيقاف الترحيل الآلي للمراجعة |
| تكرار رقم مرجع البنك | رفض التكرار حتى مع طلبين متزامنين |
| فشل إنشاء القيد أو المستند الضريبي | Rollback كامل دون حركة يتيمة |

## 6. ترتيب التنفيذ المقترح

1. **قاعدة البيانات والعزل:** تصنيف الجداول والعلاقات ومراجعة company/branch scope.
2. **اختبارات التكامل المحاسبي:** مبيعات ومشتريات ومخزون وبنوك وأصول ورواتب.
3. **مقدمات السعودية:** بناء مستند الدفعة الضريبية وتاريخ الاستحقاق والقيود والتقارير والعكس.
4. **المطابقة البنكية:** كشف بنك، مطابقة جزئية، رسوم، فروق، اعتماد التسوية.
5. **الأصول والرواتب:** إغلاق الدورات الناقصة والاختبارات النظامية.
6. **القوائم والتدفقات:** مطابقة ميزان المراجعة مع كل قائمة وتقرير.
7. **الأمان والموافقات:** مراجعة routes والصلاحيات والفترات والمرفقات.
8. **الانتقال إلى PostgreSQL:** بعد اختبار migrations والتزامن والنسخ والاستعادة.

## 7. حدود ما تم التحقق منه

- تم فحص رأس فرع التطوير والملفات الأساسية ذات الصلة على GitHub عند commit الأساس أعلاه.
- لم يتم إجراء اختبار تشغيل جديد أو تعديل بيانات شركة فعلية في هذه المراجعة.
- آخر نتيجة CI متاحة في سجل المشروع عند إعداد هذه الوثيقة كانت 324 اختبارًا ناجحًا وفحوصات Python ناجحة؛ يجب إعادة تشغيلها بعد أي تعديل برمجي جديد.
- لم يتم دمج الفرع في `main` أو نشر التطبيق.
- لا تمثل هذه الوثيقة تدقيقًا قانونيًا أو رأيًا ضريبيًا ملزمًا؛ يجب اعتماد تفاصيل المعاملات الخاصة من مختص سعودي قبل الإنتاج.
