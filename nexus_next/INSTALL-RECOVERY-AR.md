# دليل تثبيت واستكمال واستعادة Admrail ERP v2 (Windows)

> هذا الدليل جزء من حزمة Admrail بجانب ملفات التشغيل. الأولوية المطلقة هي حماية بيانات العميل. وجود قاعدة أو مستخدم سابق ليس سببًا لحذفهما أو إعادة التثبيت فوقهما.

## أوضاع التشغيل المطلوبة

يجب أن يحدد المثبت الوضع بعد الفحص، لا بالتخمين:

1. **تثبيت جديد (Fresh install):** لا يوجد ملف إعدادات صالح ولا قاعدة Admrail ولا مستخدم قاعدة بيانات مخصص. ينشئ المثبت الموارد الجديدة.
2. **استكمال تثبيت (Resume):** توجد آثار تثبيت سابق أو ملف إعدادات أو قاعدة/مستخدم، لكن بعض الخطوات لم تكتمل. يفحص ما هو موجود ويستكمل الخطوات الآمنة فقط.
3. **تحديث برنامج (Application update):** توجد نسخة Admrail سابقة وقاعدة متصلة. يحدث ملفات التطبيق أولاً بعد فحص الإصدار، ثم يأخذ نسخة احتياطية ويتحقق من الترحيلات قبل تطبيقها.
4. **استعادة (Restore):** يختار العميل نسخة احتياطية محددة ويستعيدها إلى قاعدة هدف واضحة. لا تتم الكتابة فوق قاعدة موجودة دون تأكيد صريح ونسخة احتياطية منها.
5. **تعارض أو حالة غير معروفة:** يتوقف المثبت ويصدر تقرير تشخيصي. لا يحاول إصلاح الملكية أو الصلاحيات أو كلمات المرور بطريقة عمياء.

## مصفوفة اكتشاف PostgreSQL

| قاعدة admrail_db | مستخدم admrail_app | الإجراء الآمن |
|---|---|---|
| غير موجودة | غير موجود | إنشاء الاثنين كتثبيت جديد |
| موجودة وفارغة | موجود | التحقق من المالك والاتصال ثم الاستكمال |
| موجودة وبها بيانات | موجود | الحفاظ عليها؛ نسخة احتياطية ثم فحص توافق الإصدار قبل أي Migration |
| موجودة | غير موجود | لا تنشئ مستخدمًا وتغيّر ملكية القاعدة تلقائيًا؛ افحص مالك القاعدة والكائنات ثم اعرض خطة إصلاح |
| غير موجودة | موجود | فحص المستخدم؛ يمكن إنشاء قاعدة جديدة فقط بعد تأكيد أنها تثبيت جديد |
| موجودة | موجود لكن الاتصال يفشل | تشخيص كلمة المرور/الخدمة/الصلاحيات؛ لا تحذف ولا تعيد إنشاء الموارد |
| أسماء أخرى أو قواعد متعددة | أي حالة | لا تفترض أنها تخص Admrail؛ اطلب تحديد قاعدة العميل صراحة |

## ملف الإعدادات backend/.env

- إذا كان الملف موجودًا: لا تستبدله ولا تغيّر كلمة مرور PostgreSQL. اقرأ القيم المطلوبة، تحقق من وجود المفاتيح، واختبر الاتصال بها.
- إذا كان مفقودًا مع قاعدة موجودة: لا تخمّن كلمة المرور. اطلب بيانات اتصال قاعدة التطبيق أو نفّذ مسار استعادة موثق بموافقة المسؤول.
- إذا كان تالفًا أو ناقصًا: احتفظ بنسخة منه، واعرض المفاتيح الناقصة دون طباعة كلمات المرور أو الأسرار في الشاشة أو السجل.
- لا تكتب الأسرار في ملفات عامة أو سجل التثبيت. يجب أن تكون صلاحيات ملف .env مقيدة بحسابات Windows المخولة.

## الاستكمال بعد انقطاع التثبيت

كل خطوة يجب أن تكون قابلة لإعادة التشغيل (idempotent) أو تتحقق من أثرها قبل التنفيذ:

1. فحص PostgreSQL 16 والخدمة وpsql/pg_dump.
2. قراءة الإعدادات والتحقق من اتصال التطبيق.
3. فحص قاعدة البيانات ومالكها وعدد الجداول وحالة Django migrations.
4. أخذ نسخة احتياطية قابلة للتحقق قبل أي تغيير في مخطط قاعدة بها بيانات.
5. تنفيذ migrations المعلقة فقط؛ لا تستخدم flush أو reset أو dropdb.
6. تشغيل seed_reference_data بطريقة idempotent والتحقق من وجود العملات المطلوبة دون تكرار.
7. فحص المستخدمين الإداريين وPlatformOwner؛ لا تنشئ مستخدمًا مكررًا ولا تستبدل مالكًا موجودًا.
8. اختبار Django configuration والاتصال وقائمة العملات.
9. تسجيل نتيجة كل خطوة ورمز الخطأ ووقت التنفيذ في سجل لا يحتوي كلمات مرور.

## سياسة النسخ الاحتياطي قبل التحديث

- يجب أن يكون pg_dump متاحًا وأن تنتهي عملية النسخ برمز نجاح.
- تحقق من وجود ملف النسخة وحجمه، وسجل اسم القاعدة والإصدار والتاريخ.
- لا تبدأ migrations إذا فشل النسخ الاحتياطي.
- احتفظ بالنسخة الأصلية ولا تستبدلها بنسخة لاحقة.
- اختبار الاستعادة يكون على قاعدة منفصلة؛ لا تختبر الاستعادة فوق قاعدة العميل.
- فشل migration لا يعني حذف القاعدة أو إعادة إنشائها. أوقف التشغيل، احتفظ بالنسخة والسجلات، وصدر تقريرًا.

## سيناريوهات فشل يجب اختبارها قبل إصدار المثبت

- انقطاع الكهرباء/إغلاق نافذة المثبت بعد كل خطوة من الخطوات السابقة ثم إعادة التشغيل.
- كلمة مرور PostgreSQL خاطئة أو انتهاء مهلة الاتصال.
- خدمة PostgreSQL متوقفة أو إصدار غير مدعوم.
- قاعدة موجودة ببيانات وملف .env صحيح.
- قاعدة موجودة وملف .env مفقود.
- ملف .env موجود لكن كلمة المرور أو اسم القاعدة غير صحيح.
- وجود المستخدم دون القاعدة والعكس.
- قاعدة موجودة لكن مالكها ليس مستخدم التطبيق.
- فشل pg_dump أو امتلاء القرص قبل النسخ الاحتياطي.
- فشل migration في منتصف التنفيذ.
- seed للعملات ينفذ مرتين دون تكرار.
- وجود مستخدم إداري أو PlatformOwner بالفعل.
- تحديث ملفات البرنامج مع بقاء .env وملفات الوسائط والسجلات والنسخ الاحتياطية كما هي.
- استعادة نسخة إلى قاعدة اختبار منفصلة ثم التحقق من عدد الشركات والقيود.

## شروط قبول الإصدار

لا يُعلن أن المثبت جاهز للعملاء إلا بعد نجاح اختبارات Windows فعلية للحالات التالية على قواعد منفصلة:

- تثبيت جديد من الصفر.
- استكمال تثبيت توقف في منتصفه.
- تشغيل المثبت مرة ثانية على تثبيت مكتمل (لا تغيير ضار).
- تحديث قاعدة بها بيانات اختبار حقيقية.
- اكتشاف تعارض ملكية/صلاحيات والتوقف بأمان.
- استعادة نسخة احتياطية إلى قاعدة مستقلة.
- التحقق من ظهور العملات في شاشة إنشاء الشركة.
- التحقق من عدم تغير عدد الشركات والقيود والمستخدمين بعد مسار الاستكمال غير التغييري.

## ما لا يجوز للمثبت فعله تلقائيًا

- DROP DATABASE أو DROP ROLE أو TRUNCATE أو flush.
- حذف أو إعادة تسمية backend/.env دون نسخة وموافقة.
- تغيير مالك قاعدة أو جداول موجودة دون خطة معروضة وموافقة.
- إعادة تعيين كلمة مرور مستخدم قاعدة موجود دون موافقة واضحة وتوضيح أثرها على الاتصالات الأخرى.
- استبدال ملفات media أو logs أو backups.
- استيراد بيانات نسخة SQLite القديمة تلقائيًا إلى قاعدة PostgreSQL.

## ملاحظة إصدار

هذا المستند يحدد السلوك المطلوب واختبارات القبول. وجوده بجانب البرنامج لا يعني وحده أن كل مسارات المثبت قد نُفذت أو اجتازت اختبارات Windows. يجب ربط كل بند بتنفيذ فعلي واختبار قبل تسليم حزمة عميل.
